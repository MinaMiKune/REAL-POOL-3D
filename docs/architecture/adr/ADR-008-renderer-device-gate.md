# ADR-008：Mobile 与 Compatibility 的设备实证门禁

- 日期：2026-11-11
- 状态：Proposed gate；最终渲染器选择 `BLOCKED`

## 背景

总控明确禁止仅凭理论选择渲染器。Godot 官方文档指出 Mobile 面向移动/RenderingDevice，Compatibility 面向低端/OpenGL，但项目没有设备、场景或性能数据。

## 决策

阶段 2 使用完全相同诊断内容和固定负载分别构建 Mobile 与 Compatibility，在目标设备比较正确性、视觉、帧时间、内存、启动和热稳定后才选择默认。Forward+ 排除。共同材质/灯光优先，低中高档只改表现，最终选择前 README 和风险继续标 BLOCKED。

## 备选方案

1. **直接 Mobile**：符合现代移动方向，但 Vulkan 驱动、 shader 和低端性能未知，不能预先决定。
2. **直接 Compatibility**：覆盖广且基础成本低，但视觉/扩展性和具体设备性能未知，不能预先决定。
3. **Forward+**：功能最多但官方面向桌面，移动优化不合适，排除。
4. **运行时自动切换**：可能增加启动、shader 和视觉差异复杂度；只可将渲染器作为明确构建/设置方案并实测，不承诺即时无损切换。
5. **按 GPU 名称静态白名单**：可作后续辅助，但驱动/OS 差异大，不能代替实测。

## 理由

双构建是唯一能在本项目实际资源、目标 API 和设备上公平比较的方式。球桌场景可能简单到 Compatibility 更优，也可能 Mobile 的渲染路径更合适；理论不能替代测量。

## 代价

- 需要维护两套导出/渲染验证和共同材质基线，增加早期工作量。
- 设备不足会延长 BLOCKED；不能为了进度随意关闭门禁。
- 两渲染器视觉可能有差异，需要显式降级和截图审查。

## 风险与降级

若 Mobile 在最低目标设备不可用，则默认 Compatibility；若 Compatibility 视觉/性能也不达标，降低分辨率、阴影、材质和效果并重新评估设备承诺。任何降级不得改变物理/规则/AI/LAN 结果。

## 验证方法

同机同分辨率运行固定 idle/动画/多球诊断，记录 p50/p95/p99 frame time、启动、内存、shader 错误、截图和 30 分钟热稳定。至少较新 Vulkan、低端和 sw≥600dp 设备；缺一类就明确未覆盖。最终用实测数据更新本 ADR 为 Accepted。
